# ELVARIS CAPITAL — QUANT ENGINE SECURITY SPECIFICATION (V3)

---

## 1. Security Architecture & Threat Model

QuantForge operates in an adversarial quantitative environment. Strategy code may be generated by external LLMs, mutated by genetic search, or submitted by third parties. Therefore, all strategy code is treated as **untrusted and potentially malicious**.

The engine enforces a defense-in-depth model across four independent security barriers:

```
┌─────────────────────────────────────────────────────────────┐
│                    SECURITY LAYERS                          │
├─────────────────┬───────────────────────────────────────────┤
│ Layer 1: Static │ AST policy scanner blocks banned calls,   │
│                 │ dangerous imports, and reflection tricks. │
├─────────────────┼───────────────────────────────────────────┤
│ Layer 2: AST    │ Chronological lookahead verification:     │
│ Lookahead       │ bans shift(-N), center=True, future iloc. │
├─────────────────┼───────────────────────────────────────────┤
│ Layer 3: Runtime│ Process-isolated sandbox executing in an  │
│ Jail            │ unprivileged subprocess with time limits. │
├─────────────────┼───────────────────────────────────────────┤
│ Layer 4: Data   │ Cryptographic holdout quarantine lock;    │
│ Quarantine      │ prompt firewall redaction of evaluations. │
└─────────────────┴───────────────────────────────────────────┘
```

## 2. AST Policy & Forbidden Tokens (Section 83)

Every candidate strategy is inspected by Python's `ast` module prior to execution. Any of the following tokens immediately triggers security rejection (`SANDBOX_VIOLATION`):

| Forbidden Token / Pattern | Threat Prevented | AST Enforcement |
|:---|:---|:---|
| `import os`, `subprocess`, `socket`, `sys`, `shutil` | OS shell escape / network access | `visit_Import`, `visit_ImportFrom` |
| `open()`, `eval()`, `exec()`, `compile()` | Arbitrary code execution / filesystem tampering | `visit_Call` |
| `getattr()`, `setattr()`, `hasattr()`, `delattr()` | Dynamic attribute reflection and escape | `visit_Call` |
| `__subclasses__()`, `__builtins__`, `globals()`, `locals()` | Sandbox namespace breakout | `visit_Attribute`, `visit_Name` |
| `input()`, `breakpoint()` | Process blocking and interactive execution | `visit_Call` |

## 3. Lookahead & Repainting Defenses (Sections 31, 32, 33, 84)

The engine implements 5 layers of defense to guarantee zero lookahead bias:

### Layer 1: AST Lookahead Inspection
Detects and rejects:
- Negative shifts: `df.shift(-N)` or `df.pct_change(-N)`
- Negative indexing referencing future bars
- Centered rolling windows: `rolling(..., center=True)`
- Future merge operations on misaligned timestamps

### Layer 2: Chronological Data Feeding
At runtime, `strategy.on_bar(bars)` only receives data up to the current closed bar $t$. Higher timeframe context candles are aligned only *after* their complete closing bar (no partial or future higher-timeframe bar leakage).

### Layer 3: Temporal Perturbation Testing
Features are evaluated with controlled historical offsets to verify that past signal values are completely unaffected by subsequent price action.

### Layer 4: Truncation Consistency Test
The strategy is executed on the full dataset and an abbreviated dataset truncated at bar $T$. The signals generated prior to $T$ must match with $100.0\%$ bitwise identity.

### Layer 5: Repainting Snapshot Detection
If any historical signal timestamp changes after additional bars are appended, the strategy is immediately flagged with `REPAINTING_DETECTED` and permanently barred from promotion.

## 4. Holdout Vault Quarantine (Sections 10, 85)

The Holdout dataset represents the untouched out-of-sample final exam:
1. **Isolation**: Completely inaccessible during idea generation, compilation, mutation, and initial validation.
2. **Frozen Prerequisite**: Only a strategy that has reached `FROZEN` state (with immutable code, spec, and config hashes) can request holdout access.
3. **One-Time Access Lock**: Mongo collection `holdout_access` tracks evaluation. A second request for the same strategy raises `HoldoutLockError`.
4. **Invalidation**: Any change to code or parameters breaks the hash and invalidates holdout eligibility.

## 5. Prompt Firewall (`llm/prompt_firewall.py`)

To prevent the LLM from overfitting against hidden evaluation thresholds:
- Outgoing prompts are passed through `sanitize_prompt_context`.
- Any holdout metrics (`holdout_sharpe`, `holdout_pnl`, etc.) are stripped.
- API keys, database connection strings, and server file paths are redacted using regex pattern filters (`[REDACTED_SECRET]`, `[REDACTED_PATH]`).

---

## 6. Dashboard & API Security (Section 5.4)

The FastAPI web dashboard (`dashboard/fastapi_app.py`) enforces server-side security:
- **Authentication**: Strict Bearer token / Cookie verification (`qf_token`) on all sensitive endpoints (`/api/engine/*`, `/api/strategies/*`, `/api/holdout/*`). No loopback IP bypass.
- **CSRF Protection**: Mutative HTTP methods (`POST`, `PATCH`, `DELETE`) require a valid `X-CSRF-Token` header.
- **Audit Logging**: Every administrative action is logged to the `audit_logs` collection.
